## 五、遇到的问题

### 1. 从剪辑工作台返回后项目丢失

原分析页只依赖浏览器内存保存当前任务，返回或刷新后会进入无项目状态。现已通过任务级分析地址和页面初始化恢复逻辑解决。

### 2. 长视频存在一次性吞吐和内存增长风险

原逻辑倾向于先采集整段视频的帧再集中分析，视频越长，等待时间和内存占用越明显。现已改为逻辑分块与 YOLO 有界微批；最终归并只保留轻量采样元数据。

### 3. 关键帧数量随视频长度线性增长

原界面会同时渲染所有关键帧。现按分析块分组并只展示当前分组，降低首屏 DOM 数量和图片加载压力。

### 4. Dify Agent 无法返回在线结果

配置自检最初被 Cloudflare 拒绝，补充标准请求头后已能访问服务，但当前密钥返回 HTTP 401。该问题不是必须启动本地 Dify，而是需要 Agent 成员提供与 `.env.example` 契约一致的有效 Chatflow App API Key；密钥只能通过私下安全渠道传递，不应提交到 Git。

### 5. CPU 环境下分析速度仍然偏慢

130 秒测试视频的完整分析能够通过，但 CPU YOLO 推理耗时仍较明显。当前实现优先解决峰值内存、可见进度和可恢复性，推理吞吐仍有优化空间。

## 六、下一步计划与优化建议

1. 使用 GPU、ONNX Runtime 或 TensorRT 加速 YOLO，并依据显存动态调整微批大小。
2. 将 OpenCV 按时间点随机读取改为 FFmpeg 顺序解码管道，减少长视频频繁定位造成的 I/O 开销。
3. 将分析任务迁移到持久化任务队列，为每个分析块建立检查点，支持进程重启后的断点续跑和失败块重试。
4. 将前端定时轮询升级为 Server-Sent Events 或 WebSocket，减少无效请求并降低进度反馈延迟。
5. 对小时级视频进一步采用自适应采样：低变化区降低采样率，高运动或高置信区提高采样率。
6. 将轻量采样元数据按块写入 SQLite 或分块文件，并为精彩片段和关键帧接口增加游标分页，控制多小时视频的最终内存与响应体积。
7. 为关键帧时间轴增加缩略概览、缩放和区间筛选；数据量很大时再引入列表虚拟化。
8. 配置有效的 Dify Chatflow App API Key，并补充 Agent 超时、限流、重试和可观测指标。
9. 在生产或长期运行环境设置固定的 `REELFIRE_SECRET_KEY`，避免服务重启后已有登录 Session 失效。
